# Правила работы над «Можно»

## Продукт и текущий этап

Сначала прочитай PRODUCT.md, DESIGN.md, DECISIONS.md и спецификацию текущей задачи в docs/specs/. Основой служит курсовой «Можно», отдельную идею не выбираем. Вторая пользовательская роль и окончательный состав экранов открыты, не выдавай варианты за решения.

Сейчас работают «Счета» с семью учебными кармашками на /, детали на /pockets/[id], демонстрационные состояния и образцы ДС на /design-system и /api/health. Авторизация, база, настоящие банковские операции и ИИ-функция не реализованы. Не делай запросов к API ради проверки статической страницы.

## Технологии и версии

Node 24.x, фактический локальный запуск 24.22.3; npm 11.6.2. Next.js 16.4.6, React 19.2.0, TypeScript 5.9.3, Tailwind CSS 4.3.5. Vitest 4.1.12, Playwright 1.65.0. Supabase JS 2.119.0 уже установлен шаблоном, сам сервис не подключён.

Версии сверены с node_modules 17.11.2026; package-lock.json фиксирует устанавливаемые версии, package.json может содержать диапазоны. Не обновляй зависимости ради устранения случайной ошибки. Перед кодом Next читай соответствующий раздел node_modules/next/dist/docs/, как требует служебный блок AGENTS.md.

## Команды

В корне репозитория:

- npm ci: установка по существующему package-lock.json.
- npm run dev: локальный режим разработки.
- npm run typecheck: проверка типов.
- npm test: unit-тесты.
- npm run build: проверка production-сборки.
- npx playwright install chromium: установка браузера для тестов, если его нет.
- npm run test:e2e: браузерные тесты.

Перед штатным test:e2e останови dev-процесс именно этого проекта: он запускает собственный сервер на 3100. Не останавливай неизвестные процессы. Если используешь проверенный уже запущенный dev-сервер, допускается временная проигнорированная конфигурация запуска, а ожидания продуктовых тестов остаются прежними. Записывай фактическую команду и результат.

В текущем локальном учебном окружении родительский scripts/course-npm обеспечивает Node/npm; он не входит в репозиторий и не должен быть единственным способом запуска у преподавателя. Для новой копии следуй README.

## Цикл задачи

1. Объясни Владе задачу обычными словами, назови результат и границы.
2. Предложи файлы, команды и проверки; до принятия плана не меняй код новой функции.
3. После принятия выполни работу, соблюдая границы. Изменения плана обсуждай, не записывай фиктивный апрув.
4. Покажи результат и объясни, что произошло. Различай проверку агента, понимание Влады и её приёмку.
5. Перед сохранением проверь status, diff, новые файлы, после git add проверь diff --cached. Спецификация, принятый план и запись DECISIONS должны попасть в тот же коммит, что функция.

## Проверяемые запреты

- Не добавляй и не обновляй пакеты без поручения Влады. Проверка: diff package.json и package-lock.json.
- Не подключай настоящие банковские API, платёжные SDK и переводы денег. Проверка: новые зависимости, серверные маршруты и их внешние вызовы. Это ограничение учебной версии «Можно».
- Не меняй имена и суммы в lib/demo-pockets.ts без явной задачи. Учебное упражнение с данными возможно по отдельному поручению; записывай, временная это правка или изменение продукта. Проверка: diff этого файла и результат карточек.
- Не прописывай новые цвета/отступы/радиусы прямо в карточках. Используй app/styles/tokens.css и существующий PocketCard. Проверка: diff компонентов и CSS. Новые значения сначала сверяются с ДС.
- Не меняй схему будущей базы без миграции. Проверка: файл в supabase/migrations вместе с изменением схемы.
- Не читай, не выводи и не добавляй в Git реальные .env и секреты. Для текущего экрана они не нужны; .env.example содержит только образец имён. Проверка: staged filenames и содержимое diff без печати секретов. Для отдельной задачи по API применяй безопасный процесс выбора и использования ключа.
- Не удаляй тест и не подменяй его ожидания только ради зелёного результата. При намеренном учебном дефекте исходный тест должен обнаружить нарушение, после исправления пройти. Проверка: diff tests/ и фактические результаты.
- Не выполняй commit, push, revert, смену истории или деплой без поручения, включающего соответствующее действие. Проверка: история Git и подтверждённый объём задачи. Не используй push --force как исправление неизвестной ошибки.

## Коммиты и решения

Используй feat: для новой возможности, fix: для исправления, docs: для документов. В описании поясняй зачем. Держи связанные код и доказательства одной функции вместе; не добавляй посторонние файлы через git add . без проверки.

При учебном git revert отменяй конкретный коммит ошибки кода, сохрани строку This reverts commit и объясни, что сломалось. После повторной проверки запиши исходный/обратный хеши и результат в DECISIONS.md, сохрани журнал отдельным docs-коммитом. Не выдавай ручной возврат текста за git revert.

## Общение и сохранение контекста

Общайся по-русски, на «ты», о себе в мужском роде. Новые слова объясняй сразу. После шага говори: что сделали, зачем, как работает и где посмотреть. Ручные упражнения веди по одному действию; не делай их за Владу, выдавая за её работу. При ограничении всегда дай конкретный следующий шаг. Долгие решения храни в файлах, не полагайся только на память чата.
