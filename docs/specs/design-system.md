# Первый перенос дизайн-системы «Можно»

Подготовлено 17 ноября 2026. Влада поручила подготовить соответствие и план. План принят Владой 17 ноября сообщением «газ». Первая реализация выполнена; результат визуально принят Владой («визуально ок»).

## Задача

Создать в коде общую основу оформления «Можно» и первую карточку PocketCard по существующему компоненту Figma, чтобы собирать «Счета» из повторно используемых элементов и впоследствии переносить изменения централизованно.

Основания: прочитаны текущие страницы «Дизайн-система» и «Компоненты», получены 89 определений экрана «Счета», получен high-fidelity design context и скриншот исходного PocketCard 938:3682. Исходный шаблон использует другие цвета, Arial и свою кнопку на Radix; подходящие технические части переиспользовать, оформление заменить по проверенным источникам.

- design-system/accounts-token-map.json: предложенное соответствие каждой записи с кодом. Уникальность имён проверена; составные стили и legacy-цвет помечены отдельно.

## Первый объём реализации

1. Цвета фона, карточки, текста и разделителя; шкала отступов; скругления; две исходные тени карточки; текстовые стили, нужные карточке и странице.
2. Manrope с нужными весами 500 и 600. До подключения прочитать текущую документацию Next в node_modules/next/dist/docs и выбрать воспроизводимый способ; при локальных файлах проверить источник/лицензию. Шрифт не считать подключённым до проверки загрузки в браузере.
3. PocketCard с суммой, названием и необязательной подписью. Отступ 16, скругление 24, промежуток между текстами 4; сумма Title/M 22/28, название Label/L 15/20, подпись Caption 13/18. Ширина по сетке, высота по содержимому; 172 px в мастере не превращать в жёсткую ширину для всех экранов. Статичная карточка не притворяется кнопкой.
4. Временный локальный экран проверки ДС: образцы нужных цветов, текстовых стилей и карточки, чтобы Влада могла сверить с Figma до страницы «Счета». Это техническая проверка, состав сдаваемых продуктовых экранов отдельно не меняется автоматически. Не публиковать страницу отдельно без поручения.
5. Прозрачные правила будущего обновления: храним источник/снимок/соответствие, при новом запросе читаем Figma заново, показываем diff и обновляем проверенные значения/компоненты.

Кнопку, поля, TabBar, Кэи и другие компоненты переносить отдельными шагами, когда они понадобятся. Не считать кнопку шаблона идентичной Figma-кнопке только потому, что обе называются Button. Компоненты Figma не «скачиваются» сразу с готовой логикой доступа, работы данных и анимаций.

## Как проверим

- Сверить каждую использованную настройку с прочитанной Figma и исходным мастером; использовать Title/M для суммы, а не 48 px общего остатка.
- Сверить скриншот карточки по тем же размерам/данным; размер суммы 22, текстовые веса, радиус, фон, отступы и две тени.
- Проверить фактическую загрузку Manrope и перенос длинного названия, не обрезать важную сумму.
- Изменить один токен в локальной проверке и увидеть, что его потребители обновляются; вернуть значение источника, не выдавать пробу за правку Figma.
- Typecheck, существующие unit-тесты, build; проверить стартовую страницу после изменения глобальной темы. E2E по необходимости изменённого поведения/доступности браузера.
- Показать Владе результат перед переходом к «Счетам» и сохранить фактические результаты, включая незавершённые проверки.

## Что остаётся уточнить при принятии плана

Рекомендую первый перенос ограничить основой и PocketCard. Полная библиотека сейчас добавит много компонентов, которые не нужны КТ-1. Техническую страницу образцов можно оставить локальным инструментом проверки либо после проверки удалить из продуктового маршрута, решение записать явно. Работа по учебному циклу начинается после принятия/правки этого плана; без фиктивного апрува.
